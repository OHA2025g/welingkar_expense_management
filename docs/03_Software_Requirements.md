# Zoho Expense reconstruction software requirements

This SRS defines the proposed behaviour of a new implementation derived from the inspected portal. It is intended for engineering, QA and product acceptance. Directly observed controls are referenced by OBS identifiers; behaviour requiring a saved record or external effect is an acceptance requirement until validated in a sandbox. No live mutation was used to prove these requirements.

## System boundary and execution model

The system contains an authenticated web interface, a server application with domain modules, a tenant-scoped relational database, an object store and background workers. Provider adapters handle external finance, HR, travel, messaging and analytics integrations. This architecture is proposed. The original portal's private backend and physical database were not inspected.

The server owns organization context, effective identity, permissions, lifecycle transitions, calculations, numbering, policy evaluation, approval routing and settlement. The interface provides forms and previews, but must not be trusted to enforce security or financial integrity. Server responses expose field errors, policy warnings, configuration prerequisites and stable request identifiers.

An employee's ordinary context is self-owned. On-behalf-of actions require an explicit authorized principal, a current delegation grant or a permitted administrative target-user action. The server resolves the effective scope on each request. A shared record, custom view, report definition or widget does not automatically confer access to unrelated protected data.

## Identity authorization and privacy

The 48-control permissions matrix is the observed baseline for Admin, Approver and Submitter. Admin has company-wide trip/report/card scope and reimbursement/settings rights in the inspected default. Approver has own trip/report viewing, direct approval scope and selected violation/expense-edit powers. Submitter can create/submit own reports/trips and lacks approval/settings access. Both limited roles retain selected personal card/advance, sharing, archive and delegate capabilities. The exact control values are in permissions_matrix.csv; they must be enforced independently rather than inferred from the role label alone.

Permission evaluation combines organization membership, effective actor/principal, named permission, record ownership, direct-report/approval scope, policy scope, explicit sharing, lifecycle restrictions and protected-data permission. A forbidden ID should return the agreed unavailable/denied response without exposing whether another tenant owns it. Every list, search, aggregate, export and download must apply the same authorization before user-defined filters.

Bank account numbers, travel-document identifiers, birth dates and address/identity payloads require encryption and masked display. No PAN, CVV, online-banking password or provider secret belongs in ordinary application tables or logs. OAuth or custom-service credentials are vault references. Delegation is time-bounded and cannot grant rights beyond the principal's authority. Out-of-office routing is distinct from delegation and must prevent forwarding cycles.

## Expense capture contract

Manual entry requires expense date, category and amount as displayed; currency defaults to the organization currency and reimbursement defaults to the active preference. Merchant, report, description and reference are present but not marked required in the initial form. Itemized mode requires valid category/amount per line and derives the parent total from accepted lines. Bulk entry uses a row identifier and an atomic commit contract in the initial design. Receipt-derived incomplete records may exist internally with unresolved categories, but are not equivalent to a successful manual form submission.

The server normalizes date input using the organization date format and time zone, stores dates as dates and event timestamps in UTC, and never infers a transaction date from browser locale alone. Foreign-currency amounts preserve original currency, applied rate, source and base amount. Display formatting cannot change numeric meaning. A role-restricted exchange-rate field must be protected against direct API edits.

Receipt upload is staged: request ticket, upload bytes, verify checksum/type/size, scan, extract, resolve fields and attach to the authorized record. OCR output retains field confidence and source-document references in job results. A failed scan or extraction remains visible; it cannot silently become a clean approved expense. No specific OCR accuracy or fraud-detection performance was measured in the source account.

## Report submission and approval contract

Before submission, confirm ownership, current draft/recalled state, required fields, date consistency, allowed expense associations, policy findings, validation rules and evidence completeness. Resolve the configured flow from reporting/forwarding relationships or custom rules, and persist its resolved snapshot with the report version. Create approval tasks, an audit event and notification outbox event in one transaction. Do not send an email before the transaction commits.

An approval decision checks the task assignment, delegation/OOO context, self-approval preference, allowed violation handling and current record version. Approval does not imply reimbursement. Rejection records a reason and leaves the underlying evidence/history intact. Individual expense rejection requires the separate setting and permission. Recall cancels or supersedes remaining tasks according to the approved rule and records a new revision. Export and archive are independent flags/events rather than substitute approval states.

The current report settings show a 15-day approval target and nearing-due reminders. Notification, PDF attachment and submitter-copy choices are configuration inputs. The UI states that automated reports skip report validation rules. A new implementation must either preserve that exception explicitly or record an approved deviation; silently applying inconsistent validation between entry paths is unacceptable.

## Trip and booking contract

The observed first trip form requires a name and domestic/international selection, with optional purpose. Its Save and Continue action creates the persistence boundary. The proposed later workspace contains ordered typed itinerary items, optional booking options, traveler selections, confirmations and associated advances/reports. Those detailed forms are design requirements pending sandbox reference evidence, not fully observed screens.

Travel approval, booking status and trip completion are separate state dimensions. A quote/option is not a confirmed booking. An approved trip may still await traveler selection or provider confirmation. A cancelled trip cannot be treated as fulfilled merely because a booking reference exists. Preference-controlled rules for expense date containment, report creation on cancelled trips, other travelers and automatic advances/allowances must be resolved from the active configuration rather than hardcoded.

## Advance and payment contract

An advance retains employee owner, date, original currency and amount, source account and optional trip. Current No Approval mode must be distinguished from Simple or Custom Approval. Recording an advance is a business record action; online fund transfer, if introduced, remains a separate provider-confirmed effect.

The proposed allocation model stores source-currency allocation, report-currency applied amount and conversion snapshot. Lock the advance while allocating/refunding. The sum of active source allocations plus recorded source refunds cannot exceed the original source amount. A report's advance application and an unused-advance refund are separate facts. Refunds must not be subtracted twice from the claim. The source analytics displays Refund Amount, but its exact production formula was not exercised and remains an explicit parity question.

For a synthetic example, an advance of 500 with 300 allocated and 100 returned has 100 still available. A claim with 1000 gross, 200 non-reimbursable, 300 allocated advance and 200 already reimbursed has 300 outstanding under the proposed allocation model. The returned 100 does not cause another deduction from this claim. These are design examples, not observed account transactions.

A batch can reserve only eligible approved outstanding reports, with explicit currency/source-account checks. Reserve reports transactionally and prevent a second active reservation. Before execution, re-evaluate each balance, permission and version. Store an authorized payment instruction before contacting a bank adapter. A confirmed provider result can settle the liability; an accepted request, HTTP response or queued job alone cannot.

Payment timeout after transmission is unknown_effect. Reconcile by provider idempotency/reference before any second attempt. Failures must distinguish validation/configuration errors, rejected requests, temporary provider errors and unknown outcomes. Offline reimbursement records require a reference/date/source account and audit evidence, but must not falsely claim bank-provider confirmation.

## Card reconciliation contract

Card metadata distinguishes corporate, personal and user-paid corporate cases and never stores full card secrets. Import/provider transaction identity must be unique within the card/source. Corporate auto-match/create follows active preferences; personal-card conversion remains explicit. Matching supports allocations across expenses while preventing over-allocation, repeated conversion and duplicate reimbursement. Excluded personal transactions remain in source history with reason and actor rather than disappearing.

The provider setup path includes a bank-feed agreement, which was not accepted during inspection. The reconstruction must retain the consent/version boundary and provider connection state. Import mapping, feeds, matching confidence, undo semantics and exact provider error screens require synthetic provider fixtures.

## Policy budget and metadata contract

Evaluate policy rules deterministically and return the rule ID/revision, measured fact, threshold, scope and outcome. A proposed evaluation order is field/type validation, resolved global/layout requirements, policy/category limits, custom aggregate rules, budget checks and final submission/approval gates. This precedence is a reconstruction choice that must be approved; the UI does not establish the complete engine order.

Mileage selection must preserve the source guidance's expense-created-date basis unless sandbox evidence establishes another interpretation. Capture the selected vehicle, unit, distance/odometer/GPS provenance, effective rate and rounding result. Per diem must retain location, duration, first/last-day basis, component percentages, supplements and effective rate. Do not recalculate historical approvals with a newly edited rate without a new evaluation revision.

Budgets use fiscal boundaries, configured periods and category/dimension scopes. Define whether pending, approved or reimbursed expense states consume budget before enabling blocking. Define how overlapping project/department/tag/user budgets interact, how reversals release consumption and how currency conversion is fixed. The source landing page describes warn/block capability but does not answer these detailed choices.

Field definitions are module-scoped and type-validated. Page layouts cannot enable globally disabled fields or relax global mandatory flags. Reporting-tag assignment must validate tag/option consistency and transaction/line scope. Custom actions and saved views accept only recognized fields/operators. Scripts run in an isolated capability context, never as unrestricted application database code.

## State model requirements

Proposed trip states are draft, submitted, approved, rejected, cancelled and closed, with archive tracked independently. Booking has a separate not-started/options-pending/selected/booked/failed/cancelled dimension. The visible filters support the named approval and closure states; exact transitions require sandbox validation.

Proposed report approval states are draft, submitted, partially-approved, approved, rejected and recalled. Payment states are not-due, awaiting-reimbursement, partially-reimbursed, reimbursed, failed and unknown-effect. Export and archive are independent timestamps. Approval runs carry immutable snapshots; later resubmission creates a new run/revision. A stale task cannot approve a newer report version.

Proposed job states are queued, running, retry, waiting-configuration, succeeded, failed, unknown-effect and cancelled. Progress is completed/total work units, not a timer. Retries retain stable dedupe keys. Lease expiry permits recovery only after reconciling any external effect. A cancelled UI action cannot retroactively undo a confirmed bank operation.

## Metric definitions

The following are proposed calculation contracts. Total expense equals the sum of eligible expense gross base amounts under the report's date/status scope, excluding records classified as excluded/void by the approved definition. Reimbursable claim equals eligible expense amounts marked reimbursable after accepted reductions. Outstanding reimbursement equals approved reimbursable claim less valid applied advance amount less successful reimbursements, floored at zero for the queue; employee liability is represented separately rather than hidden by the floor.

Unreported advance balance equals original amount less active applications and recorded refunds in its source currency. Pending approval count uses active submitted approval work, avoiding duplicate counting of multiple tasks for one record in record-count KPIs. Approval time is measured from the approved start/end event definition; recall/resubmission and time-zone rules must be agreed. Policy violation count distinguishes findings from unique affected expenses/reports. Budget consumption uses the approved status/currency rule and deduplicates shared dimension joins.

Every chart/report response must carry report/metric definition version, authorization scope, selected filters, date basis, currency basis and as-of timestamp. Source labels such as Total Expenses do not establish those formulas on their own. The report catalogue specifies observed columns; seeded data is required to confirm calculation parity.

## Nonfunctional requirements

Proposed performance targets are p95 under 1.5 seconds for ordinary list/detail reads and under 3 seconds for internal synchronous mutations at agreed load, excluding document processing and provider latency. Imports, exports, backups, OCR and external payments are asynchronous. These are planning targets, not measurements of Zoho. Load volume, file distribution, concurrency and data retention must be agreed before capacity estimates.

The proposed availability target is 99.9 percent for the application tier, with monitored database/object-store backups and demonstrated restoration. Recovery objectives require owner approval and restore testing; they are not established by viewing a backup button. Worker recovery must preserve idempotency and distinguish incomplete work from unknown external effects.

Security requirements include strong authentication, tenant isolation, scoped authorization, CSRF protection for cookie sessions, secure session handling, encrypted secrets/PII, safe document rendering, outbound-destination controls for webhooks, script isolation and redacted observability. Permission changes and sensitive exports must be auditable. Do not adopt the broad initial grants of a blank custom-role form as a production default without an explicit decision.

Accessibility target is WCAG 2.2 AA in the reconstructed interface, with keyboard-operable dialogs, labelled controls, focus management, readable contrast, status announcements and non-colour error cues. Support the approved desktop/tablet/mobile matrix with usable dense grids and no loss of financial meaning. The source inspection was desktop-only and did not establish its accessibility conformance.

Maintainability requires versioned schema migrations, API contracts, typed configuration, domain-level tests for money/state rules and integration adapter contracts. Observability must correlate browser request, command, audit event, job and provider reference without logging sensitive payloads. Operations need failed-job triage, reconciliation and controlled targeted replay.

## Test and release requirements

The acceptance matrix in acceptance_tests.csv is a planned test suite, not evidence of executed live tests. Validate three default-role sessions, cross-tenant ID denial, direct API calls against hidden controls, concurrent approvals/payments, retry reconciliation, currency rounding, advance/refund balances, card duplicates, layout inheritance, automation exceptions, document access, imports and all 31 standard reports.

Before production, resolve the blocking gaps, approve configuration deviations, execute provider-fake and sandbox end-to-end tests, review database/API security, complete accessibility/visual QA and demonstrate backup restoration. Financial workflows must not be certified complete solely because their initial forms were reconstructed.
